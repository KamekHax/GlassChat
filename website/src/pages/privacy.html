Privacy Policy.

This draft describes the current GlassChat Beta design as understood on 31 October 2026. It is not legal advice, a certified privacy notice, or a complete statement of live production processing.

Who operates GlassChat

GlassChat is an independent individual project operating under the name GlassChat in Denmark. No incorporated company name, operator's legal name or postal address has been supplied. For support, privacy requests, security reports and legal correspondence, contact kamekfnbr@gmail.com. The controller/operator identity and contact details require legal review before public service launch.

Current service and providers

The public information site is hosted by GitHub Pages. A temporary Render Free service in Frankfurt hosts the GlassChat API; it may sleep, start slowly, be interrupted or be taken offline. The Neon Free PostgreSQL database in Frankfurt is connected to that service and stores account/session/token records and centrally stored channel messages. The backend sends email through the Gmail API using the operator-authorized Gmail account. The owner confirmed receipt of one test email, but GlassChat registration, verification, password-reset and login flows have not been verified end to end. Email delivery and service availability are not promised for general public use.

Google processes the email recipient, message and delivery metadata under Google's own services and policies; GlassChat does not promise that Google's processing occurs only in Europe. This is a limited technical test, not an invitation to submit sensitive information. Before open account use, this draft must be updated to reflect actual processing, provider roles, transfer arrangements, lawful basis, retention and user-rights handling and receive appropriate legal review.

Information handled by the Beta source

  • Account information includes a username and email address.
  • The server stores password hashes made with Argon2id, not plaintext passwords.
  • Verification and password-reset tokens are stored as digests and expire; session records and session digests support login and revocation.
  • Channel chat includes message text, author identity, channel and timestamp. Current Beta source stores channel messages centrally in PostgreSQL as readable plaintext at the application layer.
  • The service may process IP/network request information, connection timing, user-agent data, presence and typing events while providing service.

Actual collection must be confirmed against the deployed service and its hosting/database logs before launch.

How messages are stored and protected

The current Beta is centrally operated, not local-first, and does not provide end-to-end encryption. The service and database operator can read channel message text. HTTPS/WSS protects data in transit when correctly deployed; it does not encrypt message content from the server. Do not use the current Beta for private or sensitive conversations.

This draft does not promise a message-retention period, deletion deadline or backup lifetime. The operator has not supplied a final retention schedule or user-rights workflow. Those details must be decided, implemented and reviewed before public launch.

Email verification and recovery

The backend is configured to send one-time verification and password-reset links using Gmail API/OAuth through the operator-approved sender account. The owner confirmed receipt of one direct test email. GlassChat registration, verification, reset and login flows have not been verified end to end. OAuth remains in Testing mode with a temporary refresh token, so delivery may stop. When a message is sent, Google receives the recipient address, message content and delivery metadata needed to deliver it; the public policy must be updated if the provider changes.

Cookies, local storage and the desktop client

The public website stores a theme preference in browser local storage. It does not currently implement advertising analytics. GitHub Pages may process ordinary website request metadata under its own policies. The email-action pages use one-time tokens in URL fragments and send them to the API only after the user submits the form; the website does not store those tokens in local storage.

The desktop client stores settings in its user-data directory and keeps session material in its main process, using Electron's operating-system encrypted storage when available. Current channel conversation history is on the central service, not stored as an authoritative local-only history.

See the separate Cookie & Local Storage Policy draft.

Requests and contact

For a privacy question or request, write to kamekfnbr@gmail.com. A formal identity-verification process, response timeline and complete rights-handling procedure have not yet been established. Do not email passwords, session tokens, verification/reset links or private message contents.

Before this becomes final

The project operator and qualified Danish/EU counsel must verify the controller identity, lawful basis, purpose, data inventory, processors, international transfers, retention/deletion and backup behavior, security measures, rights process and effective date. This page is a working draft; it is not a substitute for that review.
